# 🎮 Video2Team 设计文档

> **Video2Team — 把大佬的作业，改成你抄得动的作业**
>
> B站明日方舟挂机攻略视频 → AI 提取阵容 → 结合弹幕/评论区实战替代建议 + 我的干员 box → 输出一份我当前 box 能用的阵容。

---

## 1. 背景与动机

明日方舟活动关卡的经典场景：

1. 找到一挂机攻略视频，发现阵容里有干员自己没有；
2. 弹幕/评论区散落着「XX 可以用 YY 代替」的实战建议，但混在几百条无关发言里；
3. 只能一个个记下来、逐个核对自己有没有、再判断能不能用——非常累。

本项目的目标：**把这三步压缩成一次输入**。用户丢一个攻略视频（或合集）链接 + 自己的干员练度，程序输出一份「你当前 box 可用的挂机阵容」，并标注每个替换位的来源和风险。

## 2. 与 Video2Shop 的关系：同一范式的领域迁移

Video2Shop 的核心范式是三段式：**视频 → 清单 → 对比持有 → 补齐方案**。本项目完全套用，仅替换领域对象：

| | Video2Shop | Video2Team |
|---|---|---|
| 视频类型 | 美食/手工 | 活动关挂机攻略 |
| 清单 | 配方（食材+工具） | 阵容（干员+技能+部署顺序） |
| 我的持有 | 厨房已有物品 | 干员 box |
| 缺口处理 | 京东加购购买 | 替补干员填坑 |
| 增量信息源 | — | **弹幕/评论区实战替代建议（众包）** |

Video2Shop 约 60-70% 代码可直接复用（下载、抽帧 OCR、DeepSeek 双模式、GUI/Web 骨架、preflight）。

## 3. 核心设计决策（已收敛）

### 3.1 分析单元 = 单个视频

明日方舟攻略合集的典型形态是「一个关卡一个视频」的系列，而非长视频分段。因此：

- 程序以**单个视频**为分析单元：每个视频对应一个关卡，其弹幕/评论天然只讨论该关卡，**无需任何路由/分类逻辑**；
- 用户输入合集（系列）链接时，遍历每个视频独立跑管道，最后按关卡汇总；
- 长视频（一部长视频含多关）仅作为兼容场景：按弹幕时间戳 + AI 识别关卡切换做分段路由，**低优先级，v2 再考虑**。

### 3.2 box 数据源：v1 用 Excel，v2 上森空岛扫码

明日方舟无官方第三方查询 API，分两版走：

| 版本 | 方式 | 说明 |
|------|------|------|
| **v1** | **一图流导出的 Excel** | 用户在 [ark.yituliu.cn](https://ark.yituliu.cn/survey/operators)「我的干员 → 导出为 Excel」，程序解析练度表（干员名/精英化/等级/专精）。零授权、零风险、开发量最小。该格式直接定为标准输入格式 |
| **v2** | **森空岛扫码登录** | 程序展示二维码 → 用户森空岛 App 扫码 → 自动获取 cred 凭证 → 签名调 API 拉干员数据。协议已由开源社区完全逆向（[Skland_API](https://github.com/ProbiusOfficial/Skland_API)），一图流/riic.autos 均已跑通，照抄体验即可 |

备注：

- 森空岛 API 是社区逆向接口（cred + token 签名），鹰角历史上限制过第三方拉取，签名算法可能随版本变动需跟随社区维护 → **Excel 导入永远保留作为兜底**；
- 凭证安全承诺：cred 仅内存使用、不落盘（或显式加密存储并告知用户）；
- ~~截图 OCR 识别 box~~：已砍掉，有 Excel 和扫码两条更优路径。

### 3.3 替代关系：实战验证优先，知识库只做杂活

**替代关系的可靠度排序**（不可动摇）：

```
实战验证（弹幕/评论挖到的「XX换YY能过」）
  > LLM 结合关卡机制推断（喂干员属性上下文）
    > 属性相似度匹配（不做——理论相似 ≠ 实战能过）
```

干员知识库（PRTS/一图流的开源干员数据 JSON，300+ 条，本地落一份）**不承担推荐职能**，只干两件杂活：

1. **干员名字典**：AI 从弹幕/评论提取的每个干员名先查字典校验，防 LLM 幻觉出不存在的干员；
2. **属性上下文**：给 LLM 推断替代时供参考（职业/分支/费用/机制标签）。

理由：PRTS 只有属性资料、没有替代关系数据；替代是否成立取决于本关机制（快活/阻挡/对空/清杂），属性匹配推不出来。真正值钱的替代清单是玩家和 UP 主用实战验证过的——这正是弹幕/评论区挖掘的价值所在。

### 3.4 关键位 vs 工具位

挂机攻略里通常只有 1-2 个关键干员动不得，其余是灵活工具人。推荐引擎先让 AI 从解说/简介/置顶评论中标记**关键位**，替换策略分级：

- 有关键位的替换 → 高风险标注，提示「建议回评论区验证」；
- 工具位替换 → 常规标注。

推荐错了玩家会真实翻车，容错要求远高于「买错一瓶酱油」，所以**每个替换位必须带来源与风险等级**。

## 4. 系统管道

```
┌─────────────────────────────────────────────────────────────┐
│ 输入：B站攻略视频/合集链接 + box（Excel / 森空岛扫码）          │
└──────────────┬──────────────────────────────────────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ ① 阵容提取（每视频）                          │
│   优先：简介/置顶评论（UP主通常写明阵容）       │
│   兜底：下载 → 抽帧 → OCR → DeepSeek 多模态    │
│   输出：干员+技能+部署顺序+关键位标记          │
└──────────────┬──────────────────────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ ② 实战替代挖掘                                │
│   抓弹幕(XML) + 评论(API)                     │
│   → 正则粗筛 + LLM 精筛出「X→Y」映射对          │
│   → 干员名字典校验（防幻觉）                    │
└──────────────┬──────────────────────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ ③ 匹配推荐引擎                                │
│   我有 → 保留                                 │
│   没有 → 查替代映射，替代者我有 → 采用          │
│   无映射 → LLM 结合关卡机制+属性推断            │
└──────────────┬──────────────────────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ ④ 输出：最终阵容                              │
│   每个位置标注：来源（原阵容/弹幕建议/AI推断）    │
│   + 风险等级 + 评论区溯源链接                   │
└─────────────────────────────────────────────┘
```

## 5. 数据模型（核心结构）

定义见 `src/models.py`，此处为设计总览：

```
Roster（阵容）                    —— ① 的输出
 ├─ stage: str                    关卡名，如 "EX-8"
 ├─ video_id: str                 来源视频 BV 号
 ├─ slots: list[RosterSlot]
 │   ├─ operator / skill / mastery / deploy_order
 │   └─ is_key / key_reason       关键位标记及依据
 └─ source: description | pinned_comment | ocr_llm

Substitution（替代映射）          —— ② 的输出
 ├─ removed / replacement         谁被谁替
 ├─ stage                         所属关卡
 ├─ evidence                      弹幕/评论原文引用
 ├─ source: danmaku | comment | pinned
 ├─ likes                         热度，可信度权重
 └─ verified                      干员名字典校验通过

Box（干员 box）                   —— 用户输入
 ├─ operators: dict[name → OperatorEntry(name/elite/level/masteries)]
 └─ source: excel | skland

RecommendedSlot（推荐结果）       —— ③ 的输出
 ├─ original                      原阵容槽位
 ├─ final_operator / status: keep | substituted | unresolved
 ├─ via: Substitution | None      采用的实战建议
 ├─ risk: low | medium | high     关键位替换 → high
 └─ evidence_url                  评论区溯源链接
```

## 7. 数据源清单

| 数据 | 来源 | 用途 |
|------|------|------|
| 攻略视频 | B站 | 阵容提取 |
| 视频简介/置顶评论 | B站 API | 阵容提取（优先）、关键位标记 |

| 干员基础数据 | PRTS/一图流开源 JSON | 名字典 + 属性上下文（不参与推荐） |

## 8. 版本规划

### v0（MVP）—— 验证核心价值：「给出的阵容能不能过」
- 输入：单个视频链接
- box：一图流 Excel 导入
- 替代挖掘：仅该视频评论区（置顶 + 高赞优先）
- 推荐：仅「映射命中」（实战建议直接匹配），不做 LLM 推断
- 输出：最终阵容 + 来源标注

### v1 —— 完整体验
- 合集（系列）链接遍历，按关卡汇总
- 弹幕挖掘接入（正则粗筛 + LLM 精筛 + 字典校验）
- LLM 结合关卡机制 + 属性上下文的补充推断
- 关键位/工具位分级 + 风险标注 + 评论区溯源链接

### v2 —— 授权与兼容
- 森空岛扫码登录（cred 自动获取，参照一图流体验）
- 长视频分段路由 fallback（弹幕时间戳 + AI 识别关卡切换）
- 干员知识库随游戏版本更新机制

## 9. 风险与对策

| 风险 | 对策 |
|------|------|
| 替代推荐翻车（核心位被乱替） | 关键位分级 + 风险标注 + 引导回评论区验证 |
| 森空岛逆向接口被官方限制/签名变更 | Excel 导入永久保留为兜底；跟随 Skland_API 社区更新 |
| LLM 幻觉不存在的干员名 | 所有提取结果过干员名字典校验 |
| 弹幕噪音大、有效建议稀疏 | 正则粗筛 + LLM 精筛；评论区（尤其高赞）权重高于弹幕 |
| 攻略时效性（旧版本关卡） | 输出时标注视频发布时间与游戏版本（若有） |
